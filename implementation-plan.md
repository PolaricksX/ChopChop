# Implementation Plan

## Summary

Create a minimal User Pantry service and add `GET /api/v1/pantry-items/expiring`. It returns a paginated list of the authenticated caller’s items expiring from today through the requested number of days, inclusive; `days` defaults to 3 and must be between 0 and 365. Results are sorted by expiration, name, and ID; empty results return `200` with an empty page.

## Decisions

These decisions are approved for issue #6 only:

- Create the minimal User Pantry service as **one project**, `src/UserPantry/UserPantry.csproj`, with `Api/`, `Application/`, `Domain/`, and `Infrastructure/` folders, as required by `copilot-instructions.md`. Create `tests/UserPantry.Tests/` and a solution file at the repository root. This specifically approves creating a service despite issue #6’s original constraint against adding one, because no User Pantry service exists on any branch.
- Use only the approved stack: ASP.NET Core, EF Core SQL Server, xUnit (including `Microsoft.NET.Test.Sdk` and `xunit.runner.visualstudio`), `Microsoft.AspNetCore.Mvc.Testing`, and `NetArchTest.Rules`. Add no other packages.
- Add an initial migration creating the `PantryItems` table.
- Use `Guid` identifiers and nullable UTC `DateTimeOffset` for expiration.
- Add a `PantryItemResponse` DTO and `PagedResult<T>` with `items`, `page`, `pageSize`, and `totalCount`.
- Add the `pantry.read` policy and an `ICurrentUser` backed by the Development-only authentication handler.
- Return `400` when `pageSize` exceeds 100.
- Do not modify `MockClasses.cs`, `Repositories.cs`, or the `IPantry` placeholder.

## Ordered Steps

1. **Scaffold a buildable solution.** Create the solution, the single `UserPantry` service project with its four layer folders, the test project, shared build settings, package configuration, and Docker Compose SQL Server definition. Add minimal `Program.cs`, `PantryDbContext`, `ICurrentUser`, Development auth handler, and registration wiring. Include a passing test-project smoke test.
	**Why:** Establish the service foundation without leaving the first slice uncompilable.
	**Acceptance criteria:** Build and test scaffolding; Development auth configuration.
2. **Add the Domain model and initial migration.** Implement `PantryItem` with `Guid` item and owner IDs, `decimal` quantity, and nullable UTC `DateTimeOffset` expiration. Configure EF mapping, create the initial migration and snapshot, then verify SQL Server can apply it.
	**Why:** Establish the persistence shape required for the query.
	**Acceptance criteria:** Enables expiration, null-expiration, ordering, and ownership behavior.
3. **Define Application contracts and time-window logic.** Add `PagedResult<T>`, `IExpiringPantryItemsQuery`, and `GetExpiringPantryItems`. Inject `TimeProvider`; calculate the UTC range from today’s start through the start after day N, with an exclusive upper timestamp. Add the `CalculatesUtcWindow` unit test.
	**Why:** Keep time and query coordination outside the API and EF layers.
	**Acceptance criteria:** Default of 3 days and correct UTC window boundaries (verified by unit test); filtering behavior is verified by integration tests in Step 6.
4. **Implement the Infrastructure query.** Filter by owner, non-null expiration, and the calculated expiration bounds; order by expiration/name/ID ascending; count and page results; use `AsNoTracking()`; and pass `CancellationToken` through to database calls.
	**Why:** Enforce ownership, filtering, and deterministic ordering at the data boundary.
	**Acceptance criteria:** Day N included, today included for zero, already-expired excluded, null expiration excluded, pagination, empty results, sort order, and caller-only results.
5. **Expose and secure the API endpoint.** Add `pantry.read`, use `ICurrentUser` for owner identity, validate `days` and pagination at the API boundary, return `400` for page sizes above 100, map `PantryItemResponse`, and return RFC 9457 problem details with correlation ID and no stack trace. Document the success and error responses in OpenAPI.
	**Why:** Deliver the secured HTTP contract without accepting owner identity or sort choices from clients.
	**Acceptance criteria:** Invalid-input responses, authorization, ownership source, problem details, and OpenAPI.
6. **Add automated coverage.** Complete the unit test, SQL Server-backed API integration tests, OpenAPI tests, and architecture tests. Use the test database with migrations applied.
	**Why:** Verify behavior and layer boundaries with the same persistence provider used by the service.
	**Acceptance criteria:** All automated criteria in the test plan.
7. **Complete documentation and manual checks.** Write the service documentation and use the checklist below; documentation is not an automated test.
	**Why:** Make the contract, setup, boundaries, and evidence discoverable.
	**Acceptance criteria:** Documentation checklist completed.
8. **Run verification gates.** Start SQL Server and run the repository verification commands.
	**Why:** Verify the integrated solution, formatting, tests, and package audit.
	**Acceptance criteria:** All available gates pass; record any external limitation.
